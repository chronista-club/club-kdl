# コンパクト出力のインデント省略: 実装 API の測定

**[English](./indent-pack.md)** | 日本語

v0.15.0 では、コンパクト形式の対応表、共有表を使うメッセージ、表を含む自己完結ファイルのインデントを省いた。通常のライター、パーサー、名前の割り当て、対応表 ID、プロトコルバージョンは変更していない。目的はバイト数の削減であり、シリアライズやデシリアライズの高速化を保証するものではない。

## 正しさの検証

追加した 3 件のテストは、インデント付きの旧実装ですべて失敗した。実装後は compact の 13 テストと公式コーパスのテストが成功した。確認した内容は次のとおり。

- 表・メッセージ・ファイルのインデントが省かれ、通常の整形出力は変わらないこと。
- 親子構造、文字列内の空白、複数行の値、raw 文字列とエスケープ文字列、型注釈、重複プロパティ、Unicode、特殊な浮動小数点値を保つこと。
- 従来のインデント付きメッセージ・ファイル・対応表を読み込め、対応表 ID が変わらないこと。
- 公式 KDL テストの正常な文書 233 件すべてが、共有メッセージと自己完結ファイルの両形式を往復できること。出力は kdl-rs でも解析でき、意味が一致すること。

コーパステストはコーパス本体とともに配布パッケージから除外している。単独で実行できる compact の受け入れテストは含める。研究用コードは配布しない。

## バイト数: 既存の型付きベンチマーク

既存の `name_shortcuts_runtime` ベンチマークは、AST の構築、名前の検索と置換、出力を含む。自己完結形式のエンコードには対応表の構築も含める。デコードには構文解析と、derive した Rust の型への変換を含める。

| 入力 | 通常の KDL | 共有表: 変更前 → 後 | 自己完結: 変更前 → 後 |
|---|---:|---:|---:|
| 1 レコード、8 バイトの値 | 227 B | 163 → 159 B | 323 → 279 B |
| 100 レコード、各 8 バイトの値 | 16,178 B | 6,016 → 5,616 B | 6,176 → 5,736 B |
| 1 レコード、4 KiB の値 | 4,315 B | 4,251 → 4,247 B | 4,411 → 4,367 B |

別途交換する対応表は 241 B から 201 B に減る。各比較では、ペイロードを含むすべての値が変更前後で同じである。

## 処理時間: 二つの比較方法

測定日は 2026-10-30。Apple M5、macOS 27.2、rustc 1.96.0、Criterion 0.8.2 を使用した。共有マシンで、リリースビルドを単一スレッドで実行した。測っているのは経過時間であり、結果の破棄は含むがネットワーク I/O は含まない。

最初は既存の型付きベンチマークを変更前後で順に実行した。条件は 40 サンプル、ウォームアップ 200 ms、測定 1 秒。変更していない比較対象にも変動があり、100 レコードの通常エンコードは 15.92 → 17.84 µs、表の構築は 22.54 → 26.54 µs となった。この比較だけでは、インデント省略の効果を切り分けられない。推定値と 95% 信頼区間は [indent-pack-results.csv](indent-pack-results.csv) に残しているが、高速化の根拠には使わない。

二つ目の比較では、main の `3f10721` にあった旧 compact モジュールと現行モジュールを、**一つの一時的なクレートコピー**に組み込んだ。AST・derive・パーサー・値のライターは、両方で同じ現行実装を使う。旧モジュールは、元のインデント付き出力の呼び出しを保つ。この測定用コードを本体のチェックアウトには加えない。新旧どちらのデコーダーでも、両方の出力から同じ型付きオブジェクト全体を復元できることをアサーションで確認する。

この入力は 100 レコードで、各レコードに識別子・位置・可視性の 3 プロパティがある。上のバイト数測定で使った 6 プロパティの入力とは異なる。共有メッセージは 3,432 → 3,032 B、自己完結ファイルは 3,494 → 3,070 B になった。条件は 60 サンプル、ウォームアップ 300 ms、測定 2 秒、再サンプリング 10,000 回。

| 型付き API の操作 | 変更前 | 変更後 |
|---|---:|---:|
| 共有表のエンコード | 12.983 µs | 12.532 µs |
| 共有表のデコード | 19.378 µs | 19.406 µs |
| 自己完結形式のエンコード | 21.883 µs | 23.153 µs |
| 自己完結形式のデコード | 21.249 µs | 20.987 µs |

[対にした推定値と 95% 信頼区間](indent-pack-paired-results.csv)も参照。この浅い構造の入力では、**処理全体が一貫して速くなる結果は得られなかった**。共有表のエンコードは少し速く、自己完結形式のエンコードは遅くなり、デコードの差は小さい。したがって、この変更はサイズの最適化として扱う。一律の高速化とは説明しない。

[以前の探索](https://github.com/chronista-club/club-kdl/blob/v0.15.0/research/indent-pack/README.md)で確認した深いツリーのパーサー性能は、別の小規模測定の結果である。この型付き API の表に当てはめてはならない。

どちらの比較も、固定した実行順序で 1 回だけ測定している。CPU 時間、p99、RSS、圧縮、アプリケーションやネットワークの遅延は未測定。下流アプリケーションの代表的な実データでの評価は、別途行う。

## 再現方法

リポジトリのルートで、現在の実装 API のベンチマークを実行する。

```sh
cargo bench --bench name_shortcuts -- name_shortcuts_runtime --sample-size 40 --warm-up-time 0.2 --measurement-time 1 --noplot
```

同一プロセスで旧実装と現行実装を比較する場合は、先に旧ソースとローカルの依存ロックファイルを生成する。ルートのライブラリではロックファイルを追跡していない。

```sh
cargo generate-lockfile
python3 research/indent-pack/generate.py
python3 research/indent-pack/run-codec.py
```

測定用プログラムは一時コピーを使い、元のチェックアウトを保持する。Criterion の結果は `research/indent-pack/target/paired-codec-results` に出力する。入力と測定の定義は `research/indent-pack/codec_comparison.rs` にある。旧ソースの生成には、ローカルにコミット `3f10721` が必要。
